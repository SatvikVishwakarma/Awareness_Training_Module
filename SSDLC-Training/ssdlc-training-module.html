Training Overview

This module walks you through the complete Secure Software Development Lifecycle — a framework that shifts security left, embedding it proactively into every stage of development rather than bolting it on after deployment.

Why SSDLC Matters

Studies show that fixing a security flaw in production costs 30× more than fixing it during requirements. 83% of tested applications contain at least one security vulnerability. SSDLC is your blueprint to change that.

Plan & Design

Security requirements, threat modeling, and secure architecture form the bedrock before a single line of code is written.

Build & Test

Secure coding practices, peer reviews, static analysis, and dependency scanning prevent vulnerabilities from entering the codebase.

Deploy & Operate

CI/CD security gates, runtime monitoring, and incident response processes maintain security posture throughout the application lifecycle.

Module Approach

Each phase is interactive and includes real-world examples, tooling guidance, and actionable remediation steps. Hands-on labs reinforce each concept. An assessment and capstone project complete your learning journey.

1 Security Requirements OK ➡️

What it is: Security requirements define what the software must do (and must not do) from a security perspective. They are derived from business context, regulatory obligations, and threat intelligence.

Key activities:

  • Classify data assets and define sensitivity levels (PII, PCI, PHI)
  • Map applicable compliance requirements (SOC 2, GDPR, HIPAA, PCI-DSS)
  • Define authentication, authorisation, and session management requirements
  • Document cryptographic standards and key management policies
  • Establish logging, audit trail, and data retention policies

Tooling: JIRA security story templates, OWASP ASVS (Application Security Verification Standard), NIST SP 800-53 control catalogue.

Resource: OWASP ASVS

2 Threat Modeling OK ➡️

What it is: Threat modeling is a structured process to identify, quantify, and address security threats before architecture is finalised. It answers: What can go wrong- How bad would it be- What should we do about it?

Frameworks:

  • STRIDE — Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege
  • PASTA — Process for Attack Simulation and Threat Analysis (risk-centric)
  • LINDDUN — Privacy-focused threat model for data flows
  • Attack Trees — Hierarchical decomposition of attacker goals

Process: Define scope - Create Data Flow Diagrams (DFDs) - Identify trust boundaries - Enumerate threats - Rate severity (DREAD/CVSS) - Prioritise mitigations.

Tooling: Microsoft Threat Modeling Tool, OWASP Threat Dragon, IriusRisk, draw.io with STRIDE templates.

3 Secure Architecture Design OK ➡️

What it is: Translating security requirements and threat model findings into concrete architectural decisions — the blueprints that make the system defensible by default.

Core principles to apply:

  • Least Privilege — components only access what they strictly need
  • Defence in Depth — multiple independent security controls at each layer
  • Zero Trust — never trust, always verify; micro-segment services
  • Fail-Safe Defaults — default state should deny access, not grant it
  • Separation of Concerns — isolate sensitive functions (auth, payments, PII)

Patterns: API Gateway + WAF for perimeter, service mesh for east-west mTLS, secrets vault for credentials, immutable infrastructure for deployment integrity.

Tooling: AWS Well-Architected Tool, TOGAF, SABSA, Architectural Decision Records (ADRs).

4 Secure Coding Practices OK ➡️

What it is: A set of developer habits and standards that prevent common classes of vulnerability from being introduced during implementation.

Top coding rules:

  • Always use parameterised queries — never concatenate SQL with user input
  • Validate and sanitise all inputs; reject unexpected data at the boundary
  • Encode outputs context-appropriately (HTML encode for DOM, SQL escape for DB)
  • Use strong, well-vetted cryptographic libraries — never roll your own crypto
  • Store passwords with bcrypt/Argon2 (salt + high work factor); never SHA-1/MD5
  • Avoid hard-coded credentials; load secrets from environment or vault
  • Apply error handling that reveals nothing to the user; log internally

Standards: OWASP Secure Coding Practices Quick Reference, SEI CERT Coding Standards, CWE Top 25 Most Dangerous Software Weaknesses.

5 Code Review & Static Analysis OK ➡️

What it is: A combination of manual peer review (security-focused) and automated Static Application Security Testing (SAST) to identify vulnerabilities before code is merged.

Manual security code review checklist:

  • Check all entry points for input validation and sanitisation
  • Review authentication and session management logic end-to-end
  • Verify authorisation checks on every sensitive endpoint
  • Identify sensitive data in logs, error messages, or HTTP responses
  • Look for insecure direct object references (IDOR)

SAST tooling: Semgrep, SonarQube, Checkmarx, Veracode, Snyk Code, Bandit (Python), SpotBugs (Java), ESLint Security Plugin (JS/TS).

Best practice: Block PRs with critical/high SAST findings. Track findings in a Security Defect Backlog (SDB) with SLAs based on severity.

SSDLC Phases — Part 2

6 Dependency & Supply Chain Security OK ➡️

What it is: Modern software is largely composed of open-source libraries and third-party components. Supply chain attacks (e.g., SolarWinds, Log4Shell, XZ Utils) exploit trust in this dependency graph.

Key practices:

  • Generate and maintain a Software Bill of Materials (SBOM) in SPDX or CycloneDX format
  • Run Software Composition Analysis (SCA) on every build and block critical CVEs
  • Pin exact dependency versions; use lock files (package-lock.json, poetry.lock, go.sum)
  • Verify package integrity with checksums and signatures before install
  • Monitor for newly disclosed CVEs via OSV.dev, GitHub Advisory Database, or Dependabot
  • Evaluate transitive dependencies — a chain of 3 hops can hide a critical flaw

Tooling: Snyk, OWASP Dependency-Check, Trivy, Grype, Socket.dev, GitHub Dependabot, Google OSS-Fuzz.

7 CI/CD Security Integration OK ➡️

What it is: Embedding security checks as automated quality gates within the CI/CD pipeline — the DevSecOps model. Security becomes a shared responsibility across development and operations.

Pipeline security gates:

  • Pre-commit hooks: secrets detection (gitleaks, detect-secrets), lint rules
  • PR / merge gate: SAST scan, licence compliance, SBOM generation
  • Build stage: container image scanning (Trivy, Grype), SCA, signing
  • Staging deployment: DAST scan, IAST agents, API fuzzing
  • Production gate: policy-as-code (OPA/Conftest), change management approval

Tooling: GitHub Actions, GitLab CI Security, Jenkins + OWASP ZAP, Tekton Chains, Sigstore/Cosign for artefact signing, HashiCorp Vault for secrets.

Key principle: "Security as Code" — store policies, scan configs, and security tests in version control alongside application code.

8 Application Security Testing OK ➡️

What it is: A multi-layered testing strategy that exercises the application for security flaws from multiple angles — white-box, black-box, and grey-box.

Testing types:

  • SAST (Static) — analyse source code without executing (shift-left)
  • DAST (Dynamic) — probe a running application for vulnerabilities (OWASP ZAP, Burp Suite)
  • IAST (Interactive) — instrument agents observe the app during functional tests
  • Penetration Testing — manual expert-led adversarial testing on a cadence (annual minimum)
  • Fuzz Testing — supply random/mutated inputs to uncover crashes and unexpected behaviour
  • API Security Testing — validate REST/GraphQL endpoints against OWASP API Top 10

Coverage goals: Aim for 100% of critical paths covered by automated DAST or IAST in staging. Manual pen tests for privilege escalation, business logic, and auth bypass.

9 Secure Deployment OK ➡️

What it is: Hardening the runtime environment and deployment process to minimise attack surface and ensure that security configurations are consistent and immutable.

Deployment security checklist:

  • Use hardened, minimal base images (distroless, Alpine); no SSH daemons
  • Run containers as non-root; enforce read-only filesystems where possible
  • Apply Kubernetes Pod Security Standards (restricted profile); disable privilege escalation
  • Store all secrets in a vault (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager)
  • Apply network policies to limit pod-to-pod communication (zero-trust east-west)
  • Enable mTLS between services using a service mesh (Istio, Linkerd)
  • Sign container images and verify signatures at admission (Sigstore/Cosign + OPA Gatekeeper)

IaC Security: Scan Terraform/CloudFormation with Checkov, tfsec, or Snyk IaC to catch misconfigurations before provisioning.

10 Runtime Monitoring & Incident Response OK ➡️

What it is: Continuous observation of the production environment to detect attacks, anomalies, and policy violations — and a tested playbook to respond effectively when they occur.

Monitoring stack:

  • SIEM — centralised log aggregation and correlation (Splunk, Elastic SIEM, Microsoft Sentinel)
  • RASP — Runtime Application Self-Protection agents block attacks inline
  • WAF — filter malicious HTTP traffic before it reaches the application (AWS WAF, Cloudflare)
  • CSPM — Cloud Security Posture Management detects cloud misconfigurations (Wiz, Prisma Cloud)
  • EDR/XDR — endpoint and extended detection and response on hosts

Incident Response steps (PICERL): Preparation - Identification - Containment - Eradication - Recovery - Lessons Learned. Conduct tabletop exercises quarterly and full simulations annually.

Security SLOs: Define Mean Time to Detect (MTTD) and Mean Time to Respond (MTTR) targets and measure against them in dashboards.

Learning Objectives

By the end of this training, you will be able to confidently apply the following skills in your day-to-day engineering work:

  • Integrate security into development workflows — apply the "shift-left" principle by embedding security activities at requirements, design, and build stages rather than waiting for post-deployment audits.
  • Prevent OWASP Top 10 vulnerabilities — understand the root cause of injection flaws, broken authentication, SSRF, and other critical web application risks and apply mitigations proactively in code.
  • Implement DevSecOps pipelines — configure CI/CD security gates that automatically block critical vulnerabilities from reaching production, treating security as a pipeline citizen alongside tests and linting.
  • Automate security testing — leverage SAST, DAST, IAST, and fuzz testing tools to achieve continuous security coverage without slowing delivery cadence.
  • Manage software supply chain risks — generate SBOMs, enforce SCA policies, monitor for new CVEs in dependencies, and respond to supply chain compromise scenarios.
  • Conduct threat modeling sessions — lead STRIDE-based threat model workshops, produce Data Flow Diagrams, and translate threat findings into actionable security stories for the sprint backlog.
  • Design secure system architectures — apply zero-trust, least privilege, and defence-in-depth principles to create systems that are resilient against known attack patterns.
  • Operate runtime security controls — configure monitoring, alerting, and incident response playbooks to detect and respond to threats in production within defined SLO targets.

Final Capstone Project

Apply SSDLC principles end-to-end by securing a deliberately vulnerable web application (OWASP Juice Shop). Walk through each project phase below, then mark it complete.

Project Goal

Take the OWASP Juice Shop application from "vulnerable" to "production-ready" by systematically applying all ten SSDLC phases. Document your findings in a Security Remediation Report and present key metrics.

1

Define Security Requirements

Identify Juice Shop's data assets (user credentials, payment data), classify sensitivity, and write 5 ASVS-mapped security stories in your backlog.

2

Threat Model the Application

Draw a DFD for the checkout and login flows. Apply STRIDE to identify at least 8 threats. Rate each with CVSS and prioritise the top 3 for immediate remediation.

3

Run SAST & Manual Code Review

Execute Semgrep with the OWASP ruleset against the Juice Shop source. Manually review the authentication module. Document all critical and high findings with CWE references.

4

SCA & SBOM Generation

Run Trivy against the package.json. Generate a CycloneDX SBOM. Identify packages with critical CVEs and update them. Verify the build passes after upgrades.

5

Build CI/CD Security Pipeline

Create a GitHub Actions workflow that runs secrets scanning, SAST, SCA, and container image scanning. Configure the pipeline to fail on critical findings and post results as PR comments.

6

DAST Scan & API Security Testing

Run OWASP ZAP in full-scan mode against a local Juice Shop instance. Use OWASP API Security Top 10 as your checklist for the REST API endpoints. Document all confirmed vulnerabilities.

7

Remediate & Validate

Fix the top 5 vulnerabilities identified (parameterise SQL queries, add Content Security Policy headers, implement rate limiting, enforce bcrypt for passwords, sanitise output). Re-run all scans to confirm fixes.

8

Write Security Remediation Report

Produce a 1–2 page executive summary covering: vulnerabilities found, risk ratings, remediations applied, residual risk, and MTTD/MTTR metrics for any runtime monitoring configured.
